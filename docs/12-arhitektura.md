# Архитектура ForestProof

Документ отвечает на три вопроса: из чего собран сервис, куда идут данные
от контура до числа на экране и почему принято то, что принято. Он
описывает состояние на 19 сентября 2026 года.

---

## 1. Общая схема

```
                     браузер
                        │
                        ▼
              ┌───────────────────┐
              │  nginx (app/)     │  статика фронта + проксирование
              └─────────┬─────────┘
                        │ /api/ и /data/
                        ▼
              ┌───────────────────┐
              │  FastAPI (api/)   │  роутеры, роли, журнал, фоновые задачи
              └────┬─────────┬────┘
                   │         │
      ┌────────────┘         └─────────────┐
      ▼                                     ▼
┌───────────────┐                  ┌──────────────────┐
│ PostgreSQL    │                  │ forestproof_core │  формулы кейса
│ журнал, люди, │                  │ tools/           │  чтение растров
│ контуры,      │                  └────────┬─────────┘
│ задачи        │                           │
└───────────────┘                           ▼
                                  ┌──────────────────────┐
                                  │ открытые источники   │
                                  │ CEDA, Google Storage │
                                  │ LP DAAC, Element 84  │
                                  └──────────────────────┘
```

Одно правило определяет всю раскладку: **формулы живут только в
`forestproof_core/`**. `api/` и `tools/` их вызывают, интерфейс не считает
ничего — он показывает посчитанное. Поэтому число на экране, число в
ответе API и число в выгрузке JSON совпадают по построению, а не потому,
что кто-то следил за синхронностью трёх реализаций.

## 2. Слои

### `forestproof_core/` — расчётное ядро

Чистые функции без ввода-вывода: формулы кейса, перенос неопределённости,
экономика сценариев, сверка заявленных показателей, шаблонная справка.
Ничего не знает ни о сети, ни о базе, ни о файлах.

Ключевые величины: `E` (результат в т CO₂-экв.), `H` (полуширина
интервала), `E_base` (базовая линия), `R = E − E_base − LK`, доля вычета
за неопределённость, резерв `BUF`, число потенциальных единиц `Q`.

Два правила ядра, которые важнее остальных:

* **`Q` считается только при `R > 0` и `H/R < 1`.** При неположительном
  `R` отношение `H/R` не вычисляется вовсе — делить на неположительное
  бессмысленно, и в выводе стоит причина, а не число.
* **«Недоступно» ≠ «ноль».** Отсутствие данных за год даёт прочерк и
  пометку, а не подстановку соседнего значения и не ноль.

### `tools/` — данные

* `geotiff.py`, `cog.py` — свой читатель GeoTIFF, в том числе
  cloud-optimized по HTTP Range. Геобиблиотек (GDAL, rasterio) в
  зависимостях нет: это снимает самую частую причину, по которой проект
  не запускается на чужой машине.
* `fetch.py` — адреса тайлов продуктов, скачивание, кэш, запись
  происхождения рядом с каждым файлом.
* `extract_case_data.py` — сборка участка: ряды по годам, потери покрова,
  карты, рельеф, устойчивость.
* `contour_evidence.py` — снимки Sentinel-2 и гари MODIS по рамке контура.
* `build_provenance_manifest.py` — манифест происхождения опубликованных
  результатов.

`cog.py` держит постоянное TLS-соединение на читателя и кэширует читателей
по адресу. Это не оптимизация ради красоты: на одно TLS-рукопожатие в
блок сервер CEDA отвечал `DECRYPTION_FAILED_OR_BAD_RECORD_MAC` после
третьего-четвёртого запроса.

### `api/` — сервис

| Модуль | Ответственность |
|---|---|
| `routers/case.py` | расчёт по контуру: синхронный и фоновой задачей |
| `routers/contours.py` | сохранённые контуры, видимость, публикация |
| `routers/auth.py` | вход, регистрация, профиль, роли |
| `routers/admin.py` | учётные записи, роли, блокировка, источники |
| `routers/calculations.py` | журнал расчётов с авторами |
| `routers/summary.py` | краткая справка языковой моделью |
| `case_service.py` | связка ядра, данных и набора кейса |
| `jobs.py` | фоновый расчёт с состоянием в базе |
| `auth.py` | роли, пароли, токены |

### `app/` — интерфейс

React 19, TypeScript, Vite, react-router-dom 7. Сеть — только через
`src/api.ts`; второго места, которое ходит на сервер, быть не должно.
Участки набора лежат в `src/data/case-data.json` и показываются без
бэкенда: демо обязано открываться, даже когда API недоступен.

## 3. Путь данных: от контура до числа

1. **Контур.** Четыре способа задать: файл GeoJSON, обводка по карте,
   список координат, таблица-ведомость CSV. Все четыре сходятся к одному
   полигону в WGS 84 — дальше по коду разницы между ними нет.
2. **Проверка запроса.** `CalcRequest` требует ровно один источник контура
   и период по возрастанию; `geometry.py` отклоняет пустую геометрию,
   нечитаемые координаты, самопересечения и превышение 2000 га.
3. **Постановка задачи.** Расчёт по чужому контуру читает данные из сети и
   занимает минуты, поэтому идёт фоновой задачей: состояние в базе, окно
   можно закрыть, задача находится по номеру.
4. **Данные.** Порядок источников: вырезка в наборе → тайл в кэше → сам
   продукт в облаке окном по HTTP Range. Последний шаг и есть смысл
   сервиса: контур можно задать где угодно.
5. **Базовая линия.** Для участка набора — общая из
   `data/methodology/baseline.csv`. Для чужого контура выводится по
   формуле кейса из его собственной истории 2015 → 2019 и помечается как
   выведенная нами.
6. **Расчёт.** `forestproof_core` по рядам запасов.
7. **Подтверждение.** Для контура пользователя ищутся свои снимки
   Sentinel-2 и гари MODIS — по его рамке, а не родительского участка.
8. **Запись.** Расчёт попадает в журнал с автором и хешем входа. Журнал —
   не условие расчёта: если база недоступна, числа всё равно отдаются, а
   о том, что расчёта не будет в списке, сказано прямо.

## 4. Роли

Три назначаемые роли по возрастанию прав.

| Роль | Что может |
|---|---|
| **инвестор** | просмотр, денежная оценка, отбор участков |
| **оператор** | плюс загрузка контуров, расчёты, публикация своих участков |
| **администратор** | плюс учётные записи, роли, обслуживание источников |

`viewer` — не роль, а вид сервиса для того, кто ещё не вошёл. В списке
назначаемых его нет: «понизить до гостя» — действие, которого в сервисе
не существует, для этого есть блокировка.

Почему инвестор не умеет править данные: он принимает решение по числам,
и возможность их изменить у того же человека убивает смысл проверки.

Права проверяются на сервере. Список `can` в ответе `/api/auth/me` —
подсказка для отрисовки, а не ограничение: скрытая в интерфейсе кнопка
ограничением доступа не является.

**Видимость контуров.** Свой — автору, опубликованный — всем,
непубликованный чужой — администратору. Условие живёт в запросе к базе, а
не в фильтре по готовому списку: иначе чужие контуры сначала
прочитались бы, а потом «не показались», и любая ошибка в отрисовке
превращалась бы в утечку.

**Демонстрационный режим.** Сервис может открываться администратором без
входа. Подмена одна и в одном месте — в `auth.current_user`, — поэтому
ветки, в которой права разъедутся, не существует. На проде включается
только строкой `FORESTPROOF_OPEN_ADMIN=yes-i-know-this-is-public`:
случайной единицей открыть панель администратора в интернете нельзя.

Выход сильнее демонстрационного режима: `POST /api/auth/logout` ставит
куку, которая его отменяет. Без этого выход не работал вовсе — токен
снимался, сервис тут же подставлял администратора обратно.

## 5. Языковая модель

Модель **только формулирует**. Ей передаётся готовый список фактов,
посчитанных нашим кодом, и запрещено вводить величины, которых в списке
нет. Запрет держится не просьбой в промпте, а проверкой: каждое число из
ответа ищется среди переданных, и если находится лишнее — ответ
отбрасывается целиком, а на экран идёт шаблонная справка.

Поэтому «сервис ничего не выдумывает» остаётся верным, даже если модель
однажды решит дофантазировать.

Ключ живёт только на сервере и в сборку фронта не попадает. Без ключа
сервис работает штатно: справка собирается шаблоном по тем же числам.

## 6. Хранилище

| Таблица | Что хранит |
|---|---|
| `users` | учётные записи, роли, аватар, блокировка. Пароль только хешем bcrypt |
| `calculations` | расчёты целиком, с автором, версиями и хешем входа |
| `saved_contours` | загруженные контуры, их геометрия и признак публикации |
| `calc_jobs` | фоновые задачи: состояние, шаг, ошибка, результат |
| `projects`, `observations`, `disturbance_events` | набор кейса и события |
| `registry_catalog`, `plots`, `watchlist` | реестр и мастер участка |

Миграции — Alembic, `api/migrations/versions`. Перечисления объявлены с
`native_enum=False`: это обычный VARCHAR, и добавление значения не требует
отдельной миграции типа. Оборотная сторона — длина колонки берётся по
самому длинному значению на момент создания таблицы; переименование роли
в более длинное слово потребовало `alter_column` (миграция 0007).

## 7. Что сервис не делает

* Не выдаёт сертифицированные углеродные единицы. Результат — «потенциальные
  единицы по условиям кейса».
* Не устанавливает дополнительность проекта: базовая линия задана
  условиями кейса.
* Не считает причину изменения покрова без подтверждения. Потеря покрова
  по Hansen — это снижение покрова, а не установленная вырубка.
* Не подставляет числа вместо отсутствующих данных.
* Не заменяет наземные измерения: сравнение спутниковых продуктов между
  собой наземной валидацией не является.
