# ForestProof · контракты данных

Единственный источник истины по форматам обмена между звеньями. Любое расхождение с этим файлом — баг, а не «у меня так работает».

**Цепочка передачи:**

```
Р4 (геоданные по проектам) ──┐
Р5 (реестр, полигоны)        ├─→ Р3 (расчётное ядро) ─→ Р2 (API) ─→ фронт
Р5 (качество данных)         ┘         ▲
                                       │
Р5 (обучающая выборка) ─→ Р1 (модель) ─┘  подменяет эвристику внутри модуля Р3
```

---

## 0. Общие правила

**Именование.** `snake_case` во всех JSON и CSV. Никаких пробелов и кириллицы в ключах.

**Идентификаторы.** `project_id` — строка вида `proj-01`, `proj-02`, `proj-03`. Один и тот же идентификатор используется во всех файлах и таблицах.

**Единицы измерения зашиты в имя поля.** `area_ha` — гектары, `agb_t_ha` — тонны на гектар, `co2_t` — тонны CO₂-эквивалента, `rub` — рубли. Единицы не меняются нигде и никогда.

**Даты** — ISO 8601: `2026-09-18` или `2026-09-18T14:30:00Z`.

**Отсутствие данных.** `null` означает «посчитано, результата нет». Отсутствующий ключ означает «не считалось». Это разные вещи, и фронт отображает их по-разному: `null` → «данных недостаточно», отсутствие ключа → блок не показывается.

**Числа** — числами, не строками. Округление на фронте, не в данных.

**Версионирование.** Каждый расчётный артефакт несёт `methodology_version` и `algorithm_version`. При изменении формул версия поднимается.

### Обязательные правила

`observations` покрывает **непрерывный ряд лет** без пропусков в массиве. Год, по которому данных нет, присутствует со значениями `null` и `valid: false` — не выбрасывается из массива.

`agb_source_year` — год спутникового продукта биомассы, из которого взято значение. Если для 2026 года используется продукт 2022 года, здесь стоит `2022`. Это поле формирует допущение в блоке доверия к измерению.

`event_type` — строго одно из четырёх значений:

| Значение | Смысл |
|---|---|
| `fire_supported` | потеря покрова, пересекающаяся с данными о гарях |
| `non_fire` | потеря покрова без пожарных признаков. **Не «рубка»** |
| `vegetation_stress` | снижение индексов без потери покрова |
| `unknown` | событие есть, тип не определим |

`confidence` — `high`, `medium`, `low`.

`fire_evidence` — булево, независимо от `event_type`.

## 2. Р5 → Р2 · Проекты, полигоны, заявленные показатели

Файл: `data/projects.json`. Один файл на все проекты.

```json
{
  "generated_at": "2026-09-18T10:00:00Z",
  "source": "carbonreg_xlsx_2026-09-17 + manual",
  "projects": [
    {
      "project_id": "proj-01",
      "name": "Енисейский-1",
      "region": "Красноярский край",
      "mode": "with_project",

      "registry": {
        "registry_number": "КП-000123",
        "company": "ООО «Пример»",
        "methodology": "МЛ-001",
        "crediting_period_start": "2019-01-01",
        "crediting_period_end": "2029-12-31",
        "units_in_circulation": 112000,
        "source": "registry_xlsx"
      },

      "claims": {
        "forest_area_ha": 23000.0,
        "area_kind": "forest_cover",
        "agb_t_ha": 165.0,
        "expected_effect_co2_t_year": 11200.0,
        "effect_kind": "removals",
        "monitoring_date": "2026-01-15",
        "source": "registry_xlsx"
      },

      "geometry_path": "data/polygons/proj-01.geojson"
    },
    {
      "project_id": "proj-03",
      "name": "Кежемская площадка",
      "region": "Красноярский край",
      "mode": "territory_only",
      "registry": null,
      "claims": null,
      "geometry_path": "data/polygons/proj-03.geojson"
    }
  ]
}
```

### Обязательные правила

`mode` — `with_project` либо `territory_only`. При `territory_only` поля `registry` и `claims` равны `null`, блок сверки на фронте скрывается.

`claims.source` — `registry_xlsx` либо `manual`. Значение подписывается на экране: «заявлено проектом по данным реестра» либо «задано пользователем». Подмена источника без изменения этого поля недопустима.

`area_kind` — что именно означает `forest_area_ha` в отчётности проекта:

| Значение | Смысл |
|---|---|
| `forest_cover` | лесопокрытая площадь |
| `project_territory` | площадь территории проекта целиком, включая болота, реки, гари прошлых лет и прочие нелесные земли |

**Поле обязательно при `mode: with_project`.** Без него сверка площади бессмысленна: лесничество на 505 тыс. га содержит 75–85% леса, и сравнение заявленной площади территории с нашей лесопокрытой даст расхождение в двадцать процентов, целиком являющееся артефактом определения. Значение берётся из названия графы в выгрузке реестра, а не угадывается.

`effect_kind` — природа заявленного климатического эффекта:

| Значение | Смысл |
|---|---|
| `removals` | поглощение: прирост биомассы при лесовосстановлении, лесоразведении, смене режима хозяйства |
| `avoided_emissions` | предотвращённые выбросы: охрана лесов от пожаров, предотвращение обезлесения |

**Поле обязательно при `mode: with_project`.** От него зависит, сопоставим ли заявленный эффект в принципе: предотвращённые выбросы — величина контрфактическая, наблюдению со спутника не поддаётся. Правило её обработки — в разделе 6.

`monitoring_date` обязателен при `mode: with_project`: на эту дату строится вся сверка (раздел 6). Заявленные показатели без даты к сравнению не принимаются.

`geometry_path` указывает на отдельный файл GeoJSON. Геометрия **не встраивается** в `projects.json`: полигоны тяжёлые.

### Полигоны

Файл: `data/polygons/{project_id}.geojson`. Один `Feature` с геометрией `Polygon` или `MultiPolygon`, система координат **EPSG:4326** (широта/долгота в градусах). В `properties` обязателен `project_id`.

## 3. Р5 → Р3 · Качество данных

Файл: `data/quality/{project_id}.json`. Считается по флагам валидности из раздела 1 и по погрешности биомассы.

```json
{
  "project_id": "proj-01",
  "generated_at": "2026-09-19T09:00:00Z",

  "data_completeness": {
    "periods_available": 10,
    "periods_total": 12,
    "valid_coverage_pct": 93.0,
    "latest_observation_date": "2026-09-11",
    "missing_years": [2017, 2018]
  },

  "measurement_confidence": {
    "overall": "medium",
    "components": {
      "optical_coverage": "high",
      "observation_freshness": "high",
      "biomass_uncertainty": "moderate",
      "cross_source_support": "high"
    }
  }
}
```

### Обязательные правила

**Период = один год.** `periods_total` — число лет в окне наблюдения (2015–2026 включительно это 12), `periods_available` — сколько из них имеют `valid: true`. Разность обязана совпадать с длиной `missing_years`.

`measurement_confidence.components` и `overall` — только `high`, `moderate`, `low`. **Числовой оценки доверия не существует** (FR-26): ни в данных, ни на экране.

Формула каждой составляющей записывается словами в комментарий к задаче KAN-23 — на защите за неё отвечает Р1.

Если валидных наблюдений в периоде сверки нет, блок возвращается, но `overall` равен `low`, а расчётное ядро выставляет статус сверки `evidence_insufficient`.

## 4. Р5 → Р1 · Обучающая выборка

Файл: `data/ml/training_sample.csv`. UTF-8, разделитель — запятая, десятичный разделитель — точка.

| Колонка | Тип | Смысл |
|---|---|---|
| `cell_id` | str | идентификатор ячейки сетки 1×1 км |
| `lon`, `lat` | float | центр ячейки, EPSG:4326 |
| `block_id` | str | идентификатор географического блока для пространственного holdout |
| `t_year` | int | год отсчёта T |
| `target` | int | 1, если нарушение произошло в T+1…T+5, иначе 0 |
| `loss_share_5y`, `loss_share_10y` | float | доля потерь покрова за 5 и 10 лет до T |
| `years_since_loss` | float | лет с последнего нарушения; пусто, если не было |
| `treecover2000` | float | исходная лесистость, % |
| `neigh_loss_share_10km` | float | доля потерь в радиусе 10 км до T |
| `burned_share_5y`, `burned_share_10y` | float | доля выгоревшей площади за 5 и 10 лет до T |
| `years_since_fire` | float | лет с последнего пожара; пусто, если не было |
| `firms_count_10km_5y` | int | число термоточек в радиусе 10 км за 5 лет до T |
| `agb_t_ha` | float | биомасса на год ≤ T |
| `tree_share` | float | доля класса «деревья» |
| `open_share_5km` | float | доля открытых классов в радиусе 5 км — прокси фрагментации |
| `pdsi_mean_gs`, `vpd_mean_gs`, `pr_sum_gs`, `tmmx_mean_gs` | float | климат за вегетационный период, средние до T |
| `pdsi_anom_3y` | float | аномалия PDSI за 3 года до T |
| `elevation_m`, `slope_deg` | float | рельеф |
| `aspect_sin`, `aspect_cos` | float | экспозиция склона, разложенная на синус и косинус |
| `dist_road_km`, `dist_settlement_km`, `dist_river_km` | float | расстояния |
| `pop_density` | float | плотность населения |
| `is_protected` | int | 1, если ячейка в ООПТ |

### Обязательные правила

**Все признаки считаются строго по данным до `t_year` включительно.** Любой признак, использующий данные после T, делает выборку непригодной. Проверяется до обучения.

`block_id` обязателен: валидация идёт блоками по географии, случайный сплит завышает метрику из-за пространственной автокорреляции.

**Экспозиция склона раскладывается на синус и косинус, а не отдаётся в градусах.** Экспозиция циклична: 359° и 1° — соседние направления, но для дерева решений это края шкалы. Пара `aspect_sin`, `aspect_cos` снимает разрыв.

**«События не было» кодируется пустым значением, а не числом.** CatBoost обрабатывает пропуски нативно. Заглушка вида 99 воспринимается моделью как реальное расстояние в годах и искажает пороги разбиения.

Выборка **стратифицированная**: доля `target = 1` в файле не отражает природную частоту события и не используется как базовая вероятность. Отсюда требование калибровки перед любой интерпретацией выхода как вероятности.

**Окна меток пересекаются.** Для T = 2013 окно 2014–2018, для T = 2015 окно 2016–2020: три общих года. Строки не независимы, эффективный размер выборки меньше числа строк. Метрика считается только на блочном сплите.

## 5. Р1 → Р3 · Выход модели уязвимости

Модель обучена на ячейках 1×1 км, а продукт показывает уязвимость **проекта**. Правило перехода от ячеек к полигону задаётся здесь, потому что без него уровень уязвимости не определён.

Файл: `data/ml/vulnerability_{project_id}.json`.

```json
{
  "project_id": "proj-01",
  "model_version": "susceptibility-0.1",
  "generated_at": "2026-09-19T12:30:00Z",

  "cells_total": 241,
  "p_mean": 0.18,
  "p_p90": 0.34,
  "share_above_threshold": 0.11,

  "level": "low",
  "drivers": [
    "повторяющиеся пожары в радиусе 10 км",
    "близость к лесовозной дороге"
  ],

  "metrics": {
    "roc_auc": 0.74,
    "pr_auc": 0.41,
    "validation": "spatial_block_holdout"
  }
}
```

### Правило агрегации

1. Модель предсказывает калиброванную вероятность для каждой ячейки сетки, попадающей в полигон проекта.
2. `p_mean` — среднее по ячейкам, `p_p90` — 90-й процентиль, `share_above_threshold` — доля ячеек с вероятностью выше порога из конфига.
3. `level` определяется по `p_mean` двумя порогами, вынесенными в конфиг.

Пороги подбираются так, чтобы **три демо-проекта получили три разных уровня** — иначе столбец уязвимости на экране сравнения теряет смысл (KAN-35).

### Правила вывода

`drivers` — одна-три фразы **на русском языке**, из важности признаков или SHAP. Не названия колонок: «повторяющиеся пожары в радиусе 10 км», а не `burned_share_10y`.

`p_mean`, `p_p90` и `share_above_threshold` — **служебные поля для отладки и аудита.** Наружу, в API и на экран, они не попадают: пользователь видит только уровень и драйверы (FR-29).

Если модель не готова к КТ-3 (19.09, 12:00), файл не создаётся, и расчётное ядро остаётся на эвристике. Структура блока `vulnerability` в разделе 6 одинакова для обоих случаев — меняются только `method` и `model_version`.

### Определения полей, которые иначе разойдутся

**Сверка идёт на дату отчётности, а не на сегодня.** `claim_check.reference_date` равен `claims.monitoring_date`. Наблюдаемые значения во всех строках берутся из **ближайшего к этой дате валидного наблюдения**, его год записывается в `observation_year_used`. Брать последнее доступное наблюдение запрещено: если проект отчитался в 2023 году, а спутник мы считаем на 2026, расхождение вылезет у всех проектов просто оттого, что прошло три года — лес рос, где-то горел. Это будет неверное число, и оно не станет верным оттого, что все входные файлы валидны.

**События после даты отчётности — не расхождение.** Нарушения, наблюдённые позже `reference_date`, попадают в отдельный массив `events_after_reference_date` и **никогда** не влияют на `status` и не становятся строками `rows`. Отчёт, составленный в 2023 году, физически не мог содержать пожар 2026 года; трактовать это как несоответствие заявленному — ошибка. На экране блок подписывается «появилось после даты отчётности», и его смысл в том, что заявленные показатели устарели, а не в том, что они неверны.

**Площадь сравнивается только с одноимённой величиной.** Если `claims.area_kind` равен `project_territory`, строка `forest_area_ha` сопоставляется с площадью полигона, а не с лесопокрытой. Если `forest_cover` — с лесопокрытой. Смешение двух баз даёт расхождение, которого в реальности нет.

**Заявленный эффект вида `avoided_emissions` всегда `comparable: false`.** Предотвращённые выбросы — это оценка того, сколько сгорело бы без проекта. Величина контрфактическая, базовых линий мы не считаем и не претендуем. Сравнивать её с наблюдаемым изменением запаса нельзя ни при каких данных. Строка остаётся в `rows` с заполненным `reported`, пустым `observed` и пометкой о несопоставимости — пользователь должен видеть, что показатель существует и почему мы его не проверяем.

```json
{
  "metric": "expected_effect_co2_t_year",
  "reported": 361600.0,
  "observed": null,
  "observed_uncertainty": null,
  "discrepancy_pct": null,
  "comparable": false,
  "not_comparable_reason": "avoided_emissions"
}
```

**`forest_area_change_pct` и `historical_loss_share_pct` — разные величины.** Первая — чистое изменение площади покрова между первым и последним валидным годом (потери минус восстановление). Вторая — доля площади, затронутая событиями потерь за весь период, восстановление не учитывает. Они почти никогда не совпадают, и в интерфейсе подписываются разными словами.

**`recent_loss_ha` — потери за последний завершённый год наблюдения**, окно фиксируется в `recent_window_years`. Без этого поля «свежие нарушения» на экране сравнения не имеют смысла: непонятно, за какой срок.

**`fire_exposure`** — категория `low` / `medium` / `high`, выводится из пожарной истории: доля выгоревшей площади за 10 лет и число пожарных событий. Пороги в конфиге. Это **не** выход ML-модели и не то же самое, что `vulnerability`: экспозиция описывает прошлое, уязвимость — будущее.

**`area_basis`** — от какой площади считается `revenue_rub_per_ha`: `polygon` (вся площадь участка) либо `forest` (только лесопокрытая). Значение подписывается на экране, иначе два проекта нельзя сравнивать между собой.

**`price_rub_per_unit` — авторитетное значение, `price_scenario` — только ярлык.** Если пользователь задал цену вручную, `price_scenario` равен `null`, а не подгоняется под ближайший сценарий.

### Перечни допустимых значений

`claim_check.status`:

| Значение | Условие |
|---|---|
| `no_material_discrepancy` | все сопоставимые строки в пределах ±10% |
| `review_recommended` | хотя бы одна сопоставимая строка вне ±10% |
| `evidence_insufficient` | нет валидных наблюдений за период сверки |
| `not_comparable` | все строки помечены `comparable: false` |

`claims.area_kind` — `forest_cover` либо `project_territory`.
`claims.effect_kind` — `removals` либо `avoided_emissions`.
`claim_check.rows[].not_comparable_reason` — `avoided_emissions`, `area_kind_mismatch`, `no_valid_observation`. Заполняется только при `comparable: false`.
`vulnerability.level` — `low`, `medium`, `high`.
`vulnerability.method` — `heuristic` либо `model`. При `model` заполняется `model_version`.
`measurement_confidence.overall` и компоненты — `high`, `moderate`, `low`.
`fire_exposure` — `low`, `medium`, `high`.
`scenario.effect_source` — `project_reported` либо `user_defined`.
`scenario.price_scenario` — `pessimistic`, `base`, `optimistic` либо `null`.
`scenario.area_basis` — `polygon` либо `forest`.

Для `mode: territory_only` блок `claim_check` **отсутствует целиком** — ключа нет, а не `null`.

### Запреты, зашитые в контракт

В объекте `scenario` **нет** полей `units_to_issue`, `buffer_pct`, `reserve_pct`. Объём единиц к выпуску и официальный процент резервирования мы не рассчитываем.

`vulnerability` **не содержит** числовой вероятности. Только уровень и драйверы.

`haircut_pct` задаётся пользователем и **никогда** не выводится из `vulnerability`.

`co2_stock_equivalent_t_ha` называется именно так и нигде не называется «углеродными единицами».

## 8. Аудит-поля

Присутствуют в таблице расчётов с первого часа разработки. Добавить их позже — значит переписывать всё.

| Поле | Тип | Смысл |
|---|---|---|
| `calc_id` | str | `CALC-0001`, сквозная нумерация |
| `project_id` | str | ссылка на проект |
| `calculated_at` | timestamp | момент расчёта |
| `methodology_version` | str | версия методики расчёта |
| `algorithm_version` | str | версия кода расчётного модуля |
| `model_version` | str, nullable | версия ML-модели, если использовалась |
| `input_hash` | str | хеш входных данных |
| `observation_dates` | json | даты использованных наблюдений |
| `datasets` | json | наборы данных и их версии |
| `parameters` | json | все коэффициенты расчёта |
| `result` | json | полный объект результата |

**`input_hash`** — SHA-256 от канонического JSON входных данных: геоданные проекта, заявленные показатели, параметры расчёта. Ключи сортируются, пробелы убираются. Хранится **полная шестидесятичетырёхсимвольная строка**; в примерах этого файла она усечена для читаемости. Одинаковый вход обязан давать одинаковый хеш — на этом стоит вся воспроизводимость.

## 9. Мок-набор

Каталог `data/mock/` повторяет структуру реальных данных: `projects.json`, три файла `geo/{project_id}.json`, три файла `quality/{project_id}.json`, три полигона.

**Требования к мокам:**

Три проекта: один с расхождением выше 20%, один без расхождения, один в режиме `territory_only`.

Хотя бы один год с `valid: false` — чтобы фронт с первого дня умел показывать «данных недостаточно».

Хотя бы одно событие `fire_supported` и одно `non_fire`.

Три разных уровня `vulnerability_level` и три разных `fire_exposure` — иначе экран сравнения нечем проверять.

Хотя бы у одного проекта `monitoring_date` отстоит от последнего наблюдения больше чем на год, и хотя бы одно событие попадает в `events_after_reference_date` — иначе правило даты сверки не проверяется ничем.

Хотя бы один проект с `effect_kind: avoided_emissions` — чтобы строка с несопоставимым эффектом была видна на экране до защиты, а не обнаружилась на ней.

Числа правдоподобные и внутренне согласованные: площадь не растёт после потери покрова, биомасса в разумном диапазоне для бореальных лесов, `co2_stock_total_t` сходится с произведением `co2_stock_equivalent_t_ha` на площадь.

**Моки живут до конца хакатона** и используются как фикстуры для проверки фронта, когда реальные данные ломаются.

## 10. Р3 → Р2 · Краткая справка от ИИ

Справка живёт **внутри расчёта** (раздел 6, ключ `summary`), а не запрашивается страницей.

### Жёсткие правила

**Генератор получает только объект расчёта.** Ни геоданных, ни выгрузки реестра, ни файлов Р4 и Р5 он не видит. Всё, что он может сказать, уже посчитано и лежит в том же JSON.

**Генератор ничего не вычисляет.** Ни процентов, ни разностей, ни «примерно». Любое число в тексте обязано дословно присутствовать в расчёте; поля, из которых оно взято, перечисляются в `source_fields`.

**Справка неизменяема.** Один расчёт — одна справка. Пересборка создаёт **новый расчёт** с новым `calc_id`, а не переписывает старый: иначе ломается FR-70, и открытый по ссылке расчёт перестанет совпадать сам с собой.

**Запреты формулировок те же, что у интерфейса.** Не существует числовой оценки доверия (FR-36), числовой вероятности уязвимости (FR-39), слов «проект врёт» и «гринвошинг» (FR-50), слова «рубка» как типа события (FR-30).

**Если справку собрать не удалось**, ключ `summary` отсутствует целиком — блок на экране не показывается. Пустая строка или заглушка недопустимы.

### Поля

| Поле | Смысл |
|---|---|
| `text` | 2–4 предложения, без заголовков и списков |
| `generated_at` | когда собрана |
| `generator_version` | версия шаблона или модели; попадает в аудит |
| `based_on` | идентификаторы расчётов, которые перечислены под справкой на экране |
| `source_fields` | пути к полям расчёта, из которых взяты числа — для приёмки |

### Справка на экране обзора

Собирается из нескольких расчётов, поэтому лежит отдельно: `data/summary/overview.json`, та же структура, `based_on` содержит несколько идентификаторов.

## 13. Порядок изменения контракта

Контракт меняет только Р1. Изменение объявляется в общем чате с указанием, кого оно затрагивает. Молча поменянное поле — самая дорогая ошибка в команде из пяти человек: три часа на поиск, почему «у меня всё работает, а на демо пусто».
