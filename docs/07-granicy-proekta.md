# ForestProof · границы проекта и поток данных

Документ отвечает на два вопроса: **что конкретно мы делаем** и **откуда берутся данные, когда пользователь задал свой контур**. Требования — в `06-kejs-pereorientaciya.md`, здесь объём и механика.

Дата: 18.09.2026, после разбора данных кейса.

---

## 1. Что мы делаем, в одном абзаце

Веб-сервис, который по **контуру леса и паре лет** отвечает на пять вопросов подряд:

1. Сколько углерода в этом лесу было и стало.
2. Где именно он изменился и чем это подтверждается.
3. Насколько этому числу можно верить.
4. Сколько это даёт потенциальных углеродных единиц относительно заданной базовой линии.
5. Что из этого можно сохранить как отчёт и перепроверить независимо.

Всё остальное — дополнения к этим пяти.

## 2. Поток данных: откуда куда что

Самый частый вопрос: пользователь загрузил новый контур — а дальше?

```
        ПОЛЬЗОВАТЕЛЬ                    СЕРВИС                      ИСТОЧНИКИ
             │                             │                             │
  контур + пара лет  ────────────────────▶ │                             │
  (файл, обводка,                          │                             │
   координаты)                             │                             │
                                           │                             │
                            1. рамка контура                             │
                            2. какие тайлы её накрывают                   │
                                           │                             │
                                           │ ── есть в кэше? ──┐         │
                                           │                   │ нет     │
                                           │                   ▼         │
                                           │      GET тайла 10°×10° ────▶ CEDA (биомасса)
                                           │      GET тайла 10°×10° ────▶ Google (покров)
                                           │      STAC-поиск сцен  ────▶ Element 84 (снимки)
                                           │                   │         │
                                           │      сохранить в кэш        │
                                           │      + адрес, версия,       │
                                           │        дата, sha256         │
                                           │                   │         │
                                           │ ◀─────────────────┘         │
                                           │                             │
                            3. прочитать ОКНО по рамке                   │
                               (не весь тайл: 123 МБ → 48×75 пикселей)   │
                            4. доля пересечения каждого пикселя          │
                               с контуром, в гектарах                    │
                            5. биомасса → углерод → разность → CO₂       │
                            6. перенос ошибки из канала AGB_SD           │
                            7. сравнение с базовой линией → единицы      │
                                           │                             │
  результат + отчёт  ◀───────────────────  │                             │
```

### 2.1 Что уже проверено на деле

Скачали тайл `N60E030_ESACCI-BIOMASS-L4-AGB-MERGED-100m-2019-fv7.0.tif` (123 МБ) прямо с CEDA, прочитали из него окно по рамке Тверского участка и посчитали:

| | площадь | запас |
|---|---|---|
| из скачанного тайла CEDA | 1750,4839 га | 85,127113 т C/га |
| из файла набора кейса | 1750,4839 га | 85,127113 т C/га |
| эталон `baseline.csv` | — | 85,127113698 |

**Совпадение точное.** Значит путь «свой контур → открытый источник → число» замкнут и даёт правильный ответ, а не похожий.

### 2.2 Источники и их особенности

| продукт | где лежит | сетка | размер | авторизация |
|---|---|---|---|---|
| ESA CCI Biomass v7.0 | `dap.ceda.ac.uk` | тайлы 10°×10°, 100 м | ~123 МБ на год | нет |
| Hansen GFC | `storage.googleapis.com` | тайлы 10°×10°, 30 м | ~49 МБ на слой | нет |
| Sentinel-2 L2A | Element 84 Earth Search, STAC | сцены, 10—20 м | по запросу | нет |
| MODIS MCD64A1 | LP DAAC | синусоидальная, 463 м | — | **нужен Earthdata** |

Тайл покрывает 10°×10°, то есть пол-Европейской России. Поэтому **кэш окупается с первого повторного запроса**: второй участок в том же регионе не стоит ни одной загрузки.

MODIS требует учётной записи, и это единственный источник, который мы не тянем автоматически. Для четырёх участков набора данные о гарях уже есть в `events.csv`; для произвольного контура признак горения берётся из dNBR по Sentinel-2, и это оговаривается на экране.

### 2.3 Почему окно, а не весь тайл

Тайл CCI это 123 МБ сжатых и около 500 МБ в памяти. Участок кейса занимает в нём **меньше тысячной доли** — 48×75 пикселей. Читатель распаковывает только те блоки, которые задевает рамка.

Ограничение: распаковка LZW написана на Python и на больших блоках занимает секунды. Для первого запроса по новому региону это заметно, для повторных — нет, потому что работает кэш.

## 3. Что делаем и чего не делаем

### Обязательная часть

| | функция | состояние |
|---|---|---|
| 1 | Запас углерода на две даты, разность, знак, нормирование | **готово** |
| 2 | Площадное взвешивание на градусной сетке | **готово** |
| 3 | Годовой ряд и накопленное изменение | **готово** |
| 4 | Карта изменений из тех же пикселей, что и числа | **готово** |
| 5 | Снимки до и после с отбором по облачности и сезону | **готово** |
| 6 | Диапазон результата с переносом ошибки продукта | **готово**, с интерактивным разбором |
| 7 | Потенциальные единицы со всеми граничными случаями | **готово** |
| 8 | Отчёт с источниками, параметрами и допущениями | **готово** |
| 9 | Получение данных из открытого источника по параметрам | **готово** в `tools/fetch.py` |
| 10 | Произвольный контур сквозь весь расчёт | интерфейс есть, **нужен API** |

### Дополнения

| | функция | приоритет |
|---|---|---|
| A | Скрининг устойчивости результата на 2024—2029 | **готово** |
| B | Проекты: заявленное против посчитанного | P2 |
| C | Наблюдение: что изменилось с прошлого расчёта | P2 |
| D | Демонстрационный учёт происхождения единиц | не делаем |

### Не делаем сознательно

- Не устанавливаем дополнительность реального проекта.
- Не называем причину изменения покрова без подтверждения.
- Не выдаём сценарный диапазон за откалиброванный интервал.
- Не сводим показатели в один рейтинговый балл.
- Не считаем пулы кроме надземной живой биомассы.
- Не выпускаем единицы и не имитируем реестр.

## 4. Загрузка участка пользователем

### 4.1 Что можно загрузить

| способ | формат | что проверяем |
|---|---|---|
| файл границы | GeoJSON, Shapefile в zip | система координат WGS 84, полигон замкнут, без самопересечений, площадь до 20 км² |
| обводка на карте | клики по снимку | минимум 3 вершины |
| координаты | пары «широта, долгота» в текстовом поле | разбор строк, диапазоны широты и долготы |
| **таблица** | CSV или XLSX | столбцы `name`, `lat`, `lon`, `order` — по строке на вершину; несколько участков разделяются столбцом `name` |

Табличная загрузка нужна не для красоты: у лесохозяйственных организаций контуры чаще лежат в ведомостях, а не в GeoJSON. Разбор идёт на клиенте, файл на сервер целиком не уходит.

### 4.2 Что происходит с площадью больше 20 км²

Постановка ограничивает запрос двадцатью квадратными километрами. Контур больше отклоняется **до расчёта**, с указанием фактической площади — а не обрезается молча.

### 4.3 Что происходит с контуром вне покрытия

- **Вне покрытия `baseline.csv`** — запас и его изменение считаются, расчёт единиц недоступен с указанием причины. Базовая линия задана только для четырёх участков набора.
- **Внутри участка набора** — берётся удельная траектория родительского участка и фактическая площадь запроса.
- **Пересекает несколько участков** — результаты по частям суммируются.
- **Неполное покрытие растрами** — отдельно показываются рассчитанная площадь и пропуски, единицы недоступны.

## 5. Раздел «Проекты»

Возвращение первоначальной идеи в виде, который не противоречит кейсу.

**Чего нет в данных:** реестра, выгрузки, заявленных показателей. Поэтому заявленное вводит пользователь.

**Что заводится:** название, компания, период кредитования, привязка к участку или контуру, заявленный объём эффекта в т CO₂-экв., дата отчётности, вид эффекта.

**Что делает сервис:** ставит рядом посчитанное за тот же период на ту же территорию и выдаёт статус — расхождений нет, требует проверки, данных недостаточно, не сопоставимы.

**Правила сверки** переносятся из `forestproof_core/claim_check.py` без изменений: сверка на дату отчётности, сравнение только одноимённых величин, порог ±10 %, события после даты отчётности отдельно, предотвращённые выбросы несопоставимы всегда.

**Жёсткое ограничение:** расхождение с заявленным **не влияет на число потенциальных единиц**. Единицы считаются относительно базовой линии кейса. Подмешать туда заявку значит нарушить правила расчёта.

**Загрузка проектов таблицей:** CSV или XLSX со столбцами `name`, `company`, `aoi_id`, `period_start`, `period_end`, `claimed_tco2e`, `reporting_date`, `effect_kind`. Это позволяет завести десяток проектов сразу, а не по одному.

## 6. Раздел «Наблюдение»

Сейчас он показывает те же четыре участка и непонятен. Переделывается в одну понятную вещь: **что изменилось с прошлого расчёта**.

- Пользователь сохранил расчёт в журнале.
- Через время открывает участок снова.
- Сервис показывает, что изменилось во входных данных: вышла новая версия продукта, появился новый год наблюдений, нашлось новое событие.
- И говорит, стоит ли пересчитывать.

Если эту функцию не успеваем — раздел убирается до защиты, а не остаётся в виде списка без смысла.
