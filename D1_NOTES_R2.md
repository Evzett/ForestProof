# [Р2] D1 — что сделано и на каких допущениях

Реализованы все эндпоинты разделов 7 и 12 контракта (`docs/04-kontrakty-dannyh.md`),
схема БД с аудит-полями расширена (каталог реестра, участки мастера,
наблюдение), плюс мок-набор из трёх демо-участков с полигонами и превью на
диске. Ниже — решения, которые контракт оставляет открытыми, и что стоит
свериться с Р1/командой перед защитой.

## Не удалось проверить руками

Как и в `NEXT_STEPS.md` (задача A5) — в этой сессии не было рабочего
Python-интерпретатора и не поднялся Docker-демон (Docker Desktop запускал,
процесс не поднялся за ~4 минуты ожидания). Весь код написан и вычитан
вручную несколько раз, но **не запускался**. Первым делом после разбора
архива/веток:

```bash
cd api
docker compose up --build
docker compose exec api alembic upgrade head
docker compose exec api python -m app.seed
curl http://localhost:8000/api/projects
```

Если что-то не собирается или падает — это может быть опечатка, которую я
не поймал без интерпретатора под рукой.

## Решения по неоднозначностям контракта

1. **`data/` живёт внутри `api/`, не в корне репозитория.** Контракт пишет
   пути вида `data/polygons/{project_id}.geojson` без уточнения, откуда
   считать корень. `docker-compose.yml` монтирует `.:/app`, где `.` — это
   `api/` (build context Blueprint'а на Render — тоже `./api`), поэтому
   `api/data/` — единственное место, которое гарантированно попадает и в
   локальный volume, и в образ на Render без правки инфраструктуры. Если
   Р4/Р5 в будущем будут класть файлы в `data/` на уровне репозитория —
   этот путь придётся синхронизировать (симлинк или отдельный volume).

2. **`POST /api/projects/{id}/scenario` мутирует `scenario` внутри ТЕКУЩЕГО
   `calc_id`, не создаёт новую строку.** Обоснование — в самой задаче D1:
   "параметры сценария хранятся внутри расчёта, а не в браузере, иначе
   расчёт, открытый по ссылке, перестанет совпадать сам с собой". Другое
   прочтение (раздел 10, FR-70: пересборка = новый `calc_id`) отвечает на
   другой вопрос — про пересчёт ПО НОВЫМ входным данным, а не про what-if
   по тем же. См. `QUESTIONS_FOR_R1.md`, вопрос 2 — ответа от Р1 на момент
   реализации не было, выбран вариант без разрастания `calculations`.

3. **`calc_id` — глобальный автоинкремент `CALC-0001…`, без привязки к
   `project_id`.** Как и предполагалось в `QUESTIONS_FOR_R1.md`, вопрос 1.

4. **`link_project_id` в `POST /api/plots`** трактован буквально — как
   ссылка на УЖЕ существующий `projects.project_id` (докладка геометрии к
   существующему участку). Без него создаётся новый `project_id`,
   `mode: territory_only` (без `registry`/`claims` — их взять неоткуда:
   контракт не даёт эндпоинта "привязать участок к строке каталога
   реестра и создать claims"). Если сценарий мастера на самом деле другой
   (например, "оцифровать участок под конкретную строку `registry_catalog`,
   которая сейчас `no_geometry`") — это отдельный эндпоинт, которого пока
   нет, стоит уточнить у Р1/Р5.

5. **Каталог реестра (`GET /api/registry/projects`) сидируется частично.**
   Реального xlsx-импорта 132 строк не было в распоряжении — мок-набор
   содержит 10 репрезентативных строк (2 реальных посчитанных участка +
   8 заполнителей, часть которых — вымышленные компании, явно помечено в
   `api/app/seed.py`). `total`/`with_geometry` в ответе API считаются от
   фактически загруженных строк, не декларируются отдельно — так критерий
   "каталог отдаёт все проекты выгрузки одним запросом" честен для
   мок-набора. Когда появится настоящий импорт от Р5 — грузить его через
   `registry_catalog`/`registry_import_meta`, код `registry.py` менять не
   придётся.

6. **`claim_check` отсутствует для расчётов, созданных мастером
   (`POST /api/plots`).** Настоящего расчётного ядра (Р3) в этом тикете
   нет — `_build_synthetic_result` в `plots.py` кладёт правдоподобные, но
   не основанные на спутниковых данных числа, честно без сверки с
   заявленными показателями (сверка требует реального ряда наблюдений).
   Когда появится Р3 — этот генератор заменяется вызовом настоящего
   модуля, форма результата не меняется.

7. **Обнаружено расхождение фронтенда с контрактом**, не в этой задаче, но
   стоит поправить: `app/src/types.ts` определяет `Confidence` как
   `"high" | "moderate" | "low"` и использует эти значения для
   `DisturbanceEvent.confidence`. По контракту (раздел 1, строка 116)
   `confidence` события — это `high`/`medium`/`low`; `moderate` относится
   ТОЛЬКО к `measurement_confidence.overall`/`components` (раздел 3) — это
   два разных набора значений. Бэкенд в этом тикете следует контракту
   буквально (`medium` для событий), поэтому фронт на реальном API получит
   `"medium"` там, где мок сейчас показывает `"moderate"`.

## Что не входило в объём D1 и не сделано

- Настоящий расчётный модуль (Р3) — measurement/disturbances/vulnerability
  для новых участков считаются заглушкой, см. пункт 6 выше.
- RGB-композит для превью (раздел 11, основной вариант) — реализован только
  запасной (контур на заливке), рендер через Earth Engine — не зона Р2.
- Impersonation реального xlsx-импорта реестра (132 строки) — Р5.
